# Codex plugin release

`plugins/engram` is the source for the Engram Codex plugin. It contains the MCP
declaration, seven skills, nine hook events, runtime adapters, and the app icon.
Native executables and resources are generated by the signed release workflow;
installing this source directory alone does not provide the memory server.

The release produces `engram-codex-plugin-macos-arm64.tar.gz` and
`engram-codex-plugin-manifest.json`. The manifest binds every payload file to the
Engram source commit and native executable. `release-receipt.json` binds those
assets to the same release as the signed app and CLI.

## Installing a published archive

1. Download the plugin archive, manifest, and release receipt from the same
   Engram GitHub release. Verify the archive SHA-256 against the receipt.
2. Extract into a permanent directory. The archive contains an `engram` folder.
3. Ask Codex to register that folder in your personal marketplace using its
   `plugin-creator` skill. Install the resulting `engram@personal` entry through
   Codex or `codex plugin add engram@personal`.
4. Review and trust the hook definitions in Codex's Hooks settings or `/hooks`.
   The plugin initializes its host settings on the first supported hook event.

See the [plugin README](plugins/engram/README.md) for requirements, legacy
migration, policy controls, learner receipts, and current tool-failure limits.
Each colleague uses their own Codex account and memory store. The archive has no
memory database, transcript, authentication material, or deployment state.

A GitHub release asset can be shared directly. Publishing a team marketplace or
listing in the public Codex directory is a separate distribution step; neither
is implied by building this archive.

## Validation and packaging

```sh
python3 -B Tests/codex_plugin/run_suite.py
python3 -B -m unittest discover -s scripts -p 'test_package_codex_plugin.py'
python3 -B scripts/package_codex_plugin.py --help
```

The packager requires the fresh signed app's CLI directory and refuses ad-hoc
signatures, missing resources, unexpected source files, private deployment
metadata, credentials, or an inconsistent plugin version. It does not read an
installed plugin or rebuild a binary. Native MCP, signing, and natural Codex
acceptance remain separate gates; synthetic tests do not establish those passes.

Source builds use the committed SwiftPM mirror entries to resolve both upstream
SDK URL spellings to the owned SDK fork. SwiftPM consumers that build Engram as a
dependency must apply the same SDK mirror in their root package until all
transitive manifests agree on the owned URL.
